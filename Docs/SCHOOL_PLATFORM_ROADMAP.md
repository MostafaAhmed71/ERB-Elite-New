# خارطة طريق منصة المدرسة — School Operating Platform

> **مصدر الحقيقة:** `Docs/AI_PLATFORM_CONTEXT.md` + `Docs/UX_MODERNIZATION_V2_PLAN.md`  
> **نطاق المنتج:** مدرسة واحدة فقط — ليست SaaS وليست منتجاً تجارياً متعدد المدارس  
> **الهدف الاستراتيجي:** أن تصبح المنصة **النظام المركزي اليومي** الذي تعتمد عليه المدرسة في التشغيل، المتابعة، التواصل، التحفيز، المحتوى، والقرارات — مع **طبقة مطور منصة** منفصلة للصيانة والمراقبة  
> **حالة الوثيقة:** معتمدة كأساس للتطوير  
> **تاريخ التحديث:** 2026-08-01  
> **آخر تحديث جوهري:** موجة 5 — Cron موحّد + محرّر قوالب CRUD + واتساب حي من Jobs (v2.2)
> **إصدار المنصة المرجعي:** v2.2.0

---

## 0) مبادئ هذه الخارطة

1. كل اقتراح يومي يخدم **مدرسة واحدة**؛ أدوات المطور تخدم **استقرار المنصة** لا إدارة الطلاب/المعلمين كدور مدرسي.
2. **فصل الصلاحيات:** مدير المدرسة ≠ مطور المنصة. لا يُخلط Workspace التقني مع لوحات الإدارة المدرسية.
3. لا Multi-Tenant، لا Marketplace، لا White-Label تجاري، لا API عام للبيع.
4. نبني فوق الموجود: نقاط، أكاديمي، اختبارات، حضور، مسابقة، AI/RAG، واتساب، بوابات أسرة، بنك أسئلة، Audit أولي.
5. **UX Modernization v2.0** أولاً، ثم موجة البنية التحتية (ومعهما دور المطور)، ثم القيمة اليومية.
6. العمليات الطويلة تمر عبر **Job Queue**.
7. الأتمتة وتقليل النقرات أهم من تكديس الشاشات المدرسية.
8. أي مرحلة تحتاج DB أو Edge تُذكر صراحة.

## 1) تقييم الأدوار المدرسية (ملخص)

| الدور | المفتاح الحالي | الاحتياج المركزي |
|-------|----------------|------------------|
| مدير المدرسة | `principal` | قرارات يومية/أسبوعية، تشغيل مدرسي، رصيد AI للمعلمين، ليس Diagnostics العميق |
| معلم | `teacher` | يومي موحّد، قوالب، AI سياقي |
| وكيل | `deputy` | متأخرون، تصعيد، مرحلة |
| مشرف | `supervisor` | بنك أسئلة غني، تحليل→إجراء |
| رائد نشاط | `admin` | طقس نقاط/حضور/أنشطة |
| ولي أمر / طالب / مراجع | `parent` / `student` / `reviewer` | متابعة، مهمة تالية، صندوق مراجعات |

> التفاصيل السابقة للألم اليومي لكل دور ما زالت سارية؛ الإضافة الجوهرية أدناه هي **دور خارج الطبقة المدرسية**.

## 2) دور Platform Developer (System Developer) — إضافة معتمدة

### 2.1 التعريف

| البند | القيمة |
|-------|--------|
| الاسم الظاهر (عربي) | مطور المنصة |
| الاسم الإنجليزي | Platform Developer / System Developer |
| مفتاح الدور المقترح في الكود | `platform_developer` |
| الطبيعة | دور **تقني تشغيلي** — ليس مديراً ولا معلماً ولا وكيلاً |
| الجمهور | من يصون المنصة (أنت/فريق التطوير المحلي للمدرسة) |
| التسجيل العام | **ممنوع** — لا يظهر في `PUBLIC_REGISTER_ROLES` ولا في إنشاء مستخدم عادي من المدير إلا بمسار محمي/يدوي |
| الدخول بعد تسجيل الدخول | يُوجَّه إلى `/dev` فقط — لا `/dashboard` المدرسي |

### 2.2 الهدف

إنشاء **Developer Workspace** مستقل يضم أدوات المراقبة والصيانة والتشخيص وإدارة المعرفة التقنية والـ Jobs، **دون** إظهار أدوات الإدارة المدرسية (مستخدمون طلاب، نقاط، واجبات، تقييم معلمين، مسابقة كتشغيل تربوي، إلخ).

### 2.3 مكانه في المعمارية (Architecture)

```
┌─────────────────────────────────────────────────────────────┐
│                    Presentation Layer                        │
│  ┌──────────────────────────┐  ┌──────────────────────────┐ │
│  │  School App Shell        │  │  Developer Workspace     │ │
│  │  AppLayout + ROLE_NAV    │  │  DevLayout + DEV_NAV     │ │
│  │  principal, teacher,     │  │  platform_developer فقط  │ │
│  │  admin, supervisor, …    │  │  مسارات /dev/*           │ │
│  └────────────┬─────────────┘  └────────────┬─────────────┘ │
│               │ school domain                │ platform domain│
└───────────────┼──────────────────────────────┼──────────────┘
                │                              │
┌───────────────▼──────────────────────────────▼──────────────┐
│              Application / Domain Services                   │
│  academic · points · exams · parent · competition · …        │
│  + platform services: jobs · errors · audit · ai-ops · files │
└─────────────────────────────┬───────────────────────────────┘
                              │
┌─────────────────────────────▼───────────────────────────────┐
│  Infrastructure: Supabase (DB/Auth/RLS/Edge/Realtime/Storage)│
│  Hostinger (SPA + PDF upload) · VPS WhatsApp · AI providers  │
└─────────────────────────────────────────────────────────────┘
```

**قواعد معمارية:**
1. `platform_developer` لا يرث `ROLE_NAV` الخاص بـ `principal`.
2. له `DEV_NAV` + `DevLayout` منفصلان (ثيم تقني مقبول؛ بدون قوائم منح نقاط/فصول).
3. حراسة المسارات: `/dev/*` → `allowedRoles={['platform_developer']}` فقط (أو + حساب bootstrap صريح لاحقاً).
4. RLS: سياسات منفصلة للقراءة التقنية؛ **لا** صلاحات تعديل درجات طلاب أو اعتماد نقاط بحكم الدور.
5. المدير قد يرى **ملخصات مبسطة** (صحة واتساب، رصيد AI للمعلمين)؛ التفاصيل العميقة والتنفيذ الخطير (إعادة بناء Embeddings، Feature Flags النظام، Cache flush) للمطور فقط.
6. أدوات الموجة 2 (Jobs، Errors، Knowledge التقني، AI Usage التفصيلي، Audit الكامل) تُركَّب أساساً داخل `/dev/*`، مع اختصارات مدرسية محدودة حيث يلزم القرار التربوي فقط.

### 2.4 فصل الملكية: ماذا للمدير؟ ماذا للمطور؟

| القدرة | مدير المدرسة | مطور المنصة |
|--------|--------------|-------------|
| مستخدمون / طلاب / رفع جماعي | نعم | لا |
| نقاط / حضور / أنشطة / مسابقة تشغيل | نعم (حسب دوره) | لا |
| واجبات / خطط / ملاحظات | نعم | لا |
| رصيد AI للمعلمين وقوالب المدرسة التربوية | نعم (إعدادات مدرسة) | مراقبة تقنية + حدود نظام |
| رفع مستند معرفة للاستخدام التربوي | نعم (ضمن صلاحية المدرسة) | إدارة RAG التقنية، إعادة فهرسة، حذف/إعادة بناء |
| Error Center التفصيلي | ملخص أعطال تؤثر على التشغيل | كامل + فلترة + تكامل Jobs |
| Audit التربوي (من عدّل ماذا في المدرسة) | عرض مناسب للإدارة | Audit Center كامل تقني+تربوي |
| Feature Flags النظام | لا (أو إخفاء ميزات مدرسية عبر الإعداد الحالي) | نعم — إدارة مركزية |
| Jobs / Queue / OCR / Embeddings | حالة مبسطة إن لزم | تحكم كامل Retry/Cancel/Logs |
| WhatsApp QR / حالة الخادم | حالة اتصال مبسطة | مراقبة خدمة + سجلات |
| Migrations / Edge / Environment / Backup | لا | نعم |
| VERSION / Release Notes التقنية | يمكن عرض للمدرسة ملخص | Version Center كامل |
| Developer Sandbox / اختبار الخدمات | لا | نعم — بيئة آمنة للاختبار |
| Debug Mode على الواجهة | لا | نعم — للمطور فقط |
| Database Explorer | لا | نعم — **قراءة فقط** (ليس إدارة DB) |

### 2.5 صلاحيات الدور (ملخص)

**يستطيع:** Monitoring، Logs، Diagnostics، AI ops، RAG ops، Performance، System Settings التقنية، Feature Flags، Permissions التقنية، Jobs، Scheduled Tasks، Storage/DB monitors، Realtime/Supabase/WhatsApp/AI service health، **Sandbox**، **Debug Mode**، **Database Explorer (Read Only)**.

**لا يستطيع (ولا يحتاج واجهتها):** العمل كمدير/معلم/طالب/ولي أمر؛ منح نقاط؛ بناء اختبار للطالب؛ إدارة صفوف كعملية مدرسية يومية؛ تقييم معلمين؛ التواصل مع أولياء كوكيل؛ **كتابة/تعديل/حذف بيانات المدرسة عبر مستكشف القاعدة**؛ تشغيل Sandbox على بيانات الإنتاج الحساسة دون عزل.

#### د) Error Center — `/dev/errors`

الأساس (Phase E) + التوسع **Global Error Monitoring & Diagnostics (E2 / GEM)**.

يعرض ويُفلتر:
- Frontend / Unhandled Exceptions  
- Backend / DB / Edge / API  
- AI · OCR · WhatsApp · Auth · Realtime · Storage · Background Jobs  

لكل خطأ: الرسالة، Stack، الشدة، الزمن، المستخدم (اسم/دور)، المسار، المتصفح/نظام التشغيل/الجهاز، Session/Request ID، Metadata، بصمة Fingerprint مع دمج التكرار.

سير الحل: `New` → `Investigating` → `Fixed` / `Ignored` + ملاحظات مطور.

تحليلات: أكثر الصفحات/المستخدمين/الخدمات، معدل يومي، مستخدمون متأثرون.

تنبيهات لحظية داخل `DevLayout` للأخطاء الحرجة + ربط اختياري بـ WhatsApp Job (dry-run افتراضياً).

**Architecture:** التقاط خفيف من العميل (`reportPlatformError` + listeners) بدون إعاقة UX؛ حد معدل + دمج بصمة في RPC؛ Realtime على `platform_errors` للمطور فقط؛ لا يُعرَض عمق التشخيص في واجهات المدرسة.

#### هـ) Audit Center — `/dev/audit`

الحقول المعتمدة:
- المستخدم  
- العملية  
- الوحدة المتأثرة

- قبل / بعد التعديل (إن وجد)  
- الجهاز والمتصفح

- نتيجة العملية (نجاح/فشل)

يبني على `AuditLogsPage` / `complianceAudit` مع نقل الثقل إلى مساحة المطور، وإبقاء عرض إداري مبسّط للمدير عند الحاجة.

#### و) AI Monitoring — `/dev/ai/usage` (+ روابط Knowledge)

- عدد الطلبات  
- استهلاك كل مزود  
- معدل النجاح / الأخطاء  
- متوسط زمن الاستجابة  
- أكثر النماذج استخداماً  
- ربط بالأخطاء وJobs التوليد/الفهرسة  

المدير يحتفظ بإعدادات تربوية ورصيد معلمين تحت `/principal/ai-settings`؛ المطور يرى العمق التشغيلي هنا.

#### ز) Version Center — `/dev/version`

- إصدار المنصة الحالي (من `VERSION.md` / ثابت بناء)  
- سجل الإصدارات  
- آخر التحديثات  
- حالة Migrations (قائمة متوقعة مقابل المطبّق إن أمكن قياسها)  
- حالة Edge Functions (قائمة الدوال المعروفة + آخر نجاح/فشل من المراقبة)

#### ح) Developer Sandbox — `/dev/sandbox`

**الهدف:** بيئة آمنة لتجربة الخدمات التقنية **دون التأثير على بيانات التشغيل المدرسي اليومي** (قدر الإمكان عبر عزل، بيانات تجريبية، أعلام `dry-run`، أو أرقام/قنوات اختبار).

| قدرة الاختبار | الغرض |
|---------------|--------|
| Edge Functions | استدعاء دالة بمعاملات تجريبية ومشاهدة الاستجابة/الأخطاء |
| AI Prompts | تجربة نص/قالب ومزود/نموذج دون خصم غير مضبوط من رصيد المعلمين إن أمكن (حساب/وضع اختبار) |
| WhatsApp | إرسال تجريبي لرقم اختبار فقط — ممنوع البث الجماعي المدرسي من هنا |
| OCR | تمرير ملف تجريبي عبر مسار OCR ومشاهدة الناتج عبر Job |
| API | فحص مسارات/استدعاءات داخلية محددة مع عرض الزمن والحالة |
| الإشعارات | Push / قنوات إشعار تجريبية لحساب المطور |

**ضوابط إلزامية:**
- متاح لـ `platform_developer` فقط داخل `/dev`.
- لا يُستخدم كبديل لشاشات المدير (تذكير معلمين، نشر مراجعات، منح نقاط).
- كل تشغيل يُفضَّل أن يُسجَّل في Audit/Logs التقنية.
- عند الشك: الوضع الافتراضي = dry-run أو هدف اختبار صريح.

#### ط) Debug Mode — للمطور فقط

**الهدف:** وضع يُفعَّل/يُعطَّل من Workspace المطور، ويُظهر طبقة تشخيص أثناء تصفح المنصة (حتى عند فتح مسارات للمعاينة التقنية إن سُمح لاحقاً)، **دون** تمكينه لأي دور مدرسي.

| ما يُعرض أثناء التفعيل | ملاحظة |
|-------------------------|--------|
| API Response Time | زمن الاستجابات الظاهرة للعميل |
| Network Requests | قائمة طلبات مختصرة (بدون أسرار/توكنات) |
| Edge Function Logs | ملخص آخر استدعاءات مرتبطة بالجلسة إن توفرت |
| Realtime Events | أحداث القنوات المشتَركة في الجلسة |
| Console Errors | أخطاء الواجهة الملتقطة |
| Performance Metrics | مؤشرات أداء مدركة (رسم/تفاعل) |

**ضوابط إلزامية:**
- التخزين المحلي/الجلسة مرتبط بحساب `platform_developer` فقط؛ التحقق من الدور في كل تحميل.
- لا يُظهر مفاتيح API أو `service_role` أو أجسام طلبات تحتوي أسراراً.
- التعطيل الافتراضي عند الخروج؛ لا «يتسرب» لجلسة مدير/معلم.
- ليس بديلاً عن Error Center — هو طبقة لحظية أثناء التطوير والتشخيص.

#### ي) Database Explorer (Read Only) — `/dev/db`

**الهدف:** مستكشف لقاعدة البيانات **للتشخيص والفهم** داخل `/dev`، وليس أداة إدارة قاعدة بيانات (لا DDL، لا UPDATE/DELETE/INSERT من الواجهة).

| القدرة | مسموح؟ |
|--------|--------|
| استعراض قائمة الجداول | نعم |
| عدد السجلات (count) | نعم |
| البحث داخل البيانات / عرض صفوف | نعم — مع حد صفحات وحقول حساسة مُقنَّعة عند الحاجة |
| تصدير CSV لعينة/نتيجة قراءة | نعم — بحجم محدود ومُسجَّل في Audit |
| استعلامات قراءة فقط (`SELECT` / مكافئ آمن) | نعم — عبر مسار مقيّد يرفض أي كتابة |
| تعديل مخطط، سياسات، حذف، تحديث جماعي | **لا** |
| تشغيل SQL حر غير مفلتر | **لا** — قائمة بيضاء لقراءة فقط أو باني استعلام محدود |

**ضوابط إلزامية:**
- فصل كامل عن أدوات إدارة المدرسة؛ المدير لا يصل `/dev/db`.
- RLS/دالة `SECURITY DEFINER` للقراءة بحذر، أو Edge Function مخصّصة للـ read-only مع timeout وحد صفوف.
- إخفاء/تقنيع حقول حساسة (هواتف، كلمات مرور hashes، توكنات) حسب سياسة واضحة.
- لا يُستبدل به Supabase Dashboard للعمليات الإدارية الخطرة؛ الغرض تشخيص وصيانة طويلة الأمد فقط.

### 2.7 ROLE_NAV المقترح للمطور (`DEV_NAV`) — مجموعات

1. **الرئيسية** → `/dev`  
2. **الصحة والمراقبة** → Health، Errors، Performance، Realtime، Supabase، WhatsApp، AI services  
3. **المهام والطوابير** → Jobs، Queue، Schedules، OCR  
4. **البيانات والملفات** → Files، Storage monitor، Database monitor، **Database Explorer (RO)**  
5. **الذكاء والمعرفة** → Knowledge، Embeddings/Reindex، AI Usage  
6. **التطوير والتشخيص** → **Sandbox**، **Debug Mode**، Logs، Cache  
7. **الأمان والامتثال** → Audit، Permissions، Feature Flags  
8. **الإصدارات والبيئة** → Version Center، Release Notes، Environment، Backup  

لا تُدرج عناصر مدرسية في هذه القائمة.

### 2.8 متطلبات تقنية عند التنفيذ لاحقاً (توثيق فقط)

| المتطلب | التفصيل |
|---------|---------|

## 11) قواعد التنفيذ لاحقاً

1. المصدر: هذه الوثيقة + `AI_PLATFORM_CONTEXT.md` + `UX_MODERNIZATION_V2_PLAN.md`.  
2. عند تنفيذ C0: حدّث أيضاً سياق المنصة (`UserRole` في الوثائق) قبل توسيع الشاشات.  
3. لا تُوضع أدوات خطرة (Cache flush، Reindex كامل، Feature Flags النظام، Sandbox، Debug Mode، DB Explorer) تحت `principal`.  
4. لا OCR/Embeddings/واتساب جماعي خارج Jobs بعد اكتمال C.  
5. Database Explorer = قراءة فقط دائماً؛ أي حاجة لكتابة تتم عبر migrations/سكربتات منضبطة خارج هذه الشاشة.  
6. Sandbox يستخدم أهداف اختبار / dry-run؛ ممنوع البث لبيانات أولياء/معلمين الحقيقية كمسار افتراضي.  
7. ZIP + `VERSION.md` قبل كل مرحلة كبيرة.  
8. اختبار مزدوج: حساب مطور يرى `/dev` فقط؛ حساب مدير لا يرى `/dev` ولا Debug Mode.

## 12) الخلاصة التنفيذية

المنصة تحتاج طبقتين واضحتين:

1. **School Operating Layer** — أدوار المدرسة والعمل اليومي التربوي.
